# Фронтенд «Запас»

React + JavaScript, Vite, Bootstrap 5.3.3, React Bootstrap, React Router и TanStack Query.
Оформление перенесено из `../mockups/zapas-dashboard.html`; исходный макет сохранён.

## Запуск

Из этой папки:

```sh
npm ci
npm run dev
```

Интерфейс: http://localhost:5173. Нужен запущенный бэкенд на порту 8080
(инструкция запуска Docker Compose находится в корневом README).
Vite проксирует `/api` и `/health` на `http://127.0.0.1:8080`.
Проверенная версия Node.js — 20.16.0.

Для другого клиента или адреса API скопируйте `.env.example` в `.env.local`
и задайте `VITE_CLIENT_ID` и `VITE_API_BASE_URL`. После изменения перезапустите Vite.
По умолчанию выбран клиент `anya`. Настройки VITE публичны: секреты в них не хранить.

```sh
npm run build
npm run preview
```

Сборка находится в `dist/`. Прокси Vite работает только в режиме разработки.
При размещении сборки сервер должен проксировать `/api` к бэкенду либо нужно
задать `VITE_API_BASE_URL` перед сборкой и настроить CORS на бэкенде.
Маршруты `/savings`, `/transactions`, `/recurring`, `/decisions`, `/onboarding`
должны отдавать `index.html` при прямом открытии.

## Организация

- `src/app` — настройки, провайдер запросов и уведомлений, маршрутизация.
- `src/layouts` — общая шапка, навигация и модалки.
- `src/pages` — сборка экранов.
- `src/features` — API, хуки и компоненты копилки, правила, операций, решений,
  регулярных платежей и анкеты.
- `src/shared` — общий fetch-клиент, элементы интерфейса, деньги и даты.
- `src/styles/theme.css` — стили исходного макета; `global.css` — дополнения React.

Деньги хранятся и отправляются целыми копейками. Поля ввода принимают рубли,
преобразование выполняется при отправке. Даты показываются в Europe/Moscow.
Данные сервера хранятся в TanStack Query, поля форм и открытые окна — в React.
Изменения подтверждаются ответом сервера; при ошибке данные не подменяются
фиктивным успехом. Балансы и вопросы перечитываются каждые 15 секунд,
при возвращении в окно и после изменений. Встроенные повторы финансовых
POST-запросов выключены.

## Подключение копилки

1. Новый клиент заполняет анкету кнопкой «Проверить анкету».
2. Только после ответа `eligible: true` появляется «Настроить правило».
3. Кнопка «Подключить копилку» сохраняет правило. После успешного ответа
   открывается главная с подключённой копилкой.

До подключения разделы истории и платежей показывают следующий шаг настройки,
а не ошибки отсутствующего клиента. При отказе анкеты правило недоступно.
В `sessionStorage` сохраняются только ID клиента, итог допуска и режим, чтобы
можно было продолжить второй шаг после перезагрузки вкладки. Данные полей
анкеты не сохраняются. Это подсказка для UI: сервер повторно проверяет допуск
при сохранении правила. При конфликте 409 клиент возвращается к анкете.

## Ограничения контракта 0.5.0

1. **Нет GET `/rule`.** Форма использует только значения из подтверждённых
   PUT/PATCH текущей сессии. После перезагрузки неизвестные процент и срок
   нужно указать заново. Перед полной заменой правила показана подсказка;
   дополнительные пороги доступны в раскрывающемся блоке. Изменение паузы
   отправляет только `PATCH { paused }` и не заменяет остальные настройки.
   Доход в правиле отдельно не запрашивается: `declared_income` не передаётся,
   бэкенд берёт его из последней анкеты.
   Для полноценного редактирования нужен GET `/api/clients/{id}/rule`.
2. **Нет актуального расчёта в `/savings`.** Главная показывает объяснение
   последнего решения, только если у него есть `explanation` и режим `smart`.
   У суммы подписана дата расчёта. Это исторический расчёт, а не обещание
   текущей доступной суммы. В `simple` и при отсутствии объяснения показан прочерк.
3. **Нет GET анкеты.** Поля не заполняются выдуманными персональными данными.
   Повторная анкета заменяет прежнюю; отказ при HTTP 200 показывается отдельно
   от ошибки запроса. Одобрение новой анкеты предлагает создать правило.
4. **Нет авторизации в MVP.** Клиент задаётся в конфигурации. Банковские
   `POST /api/transactions` и `POST /api/events/account` не входят в клиентский UI.
5. У списков есть только `limit`, без курсора. Можно расширить выборку с 50
   до 200 записей; после этого интерфейс явно сообщает ограничение.

При потере ответа на снятие его ID и сумма сохраняются в `sessionStorage`
для этого клиента. Повтор после закрытия модалки или перезагрузки вкладки
использует тот же ID, включая случай, когда сервер уже изменил баланс.
После подтверждённого результата запись удаляется. До получения результата
сумма этой попытки заблокирована для редактирования.

## Сценарии показа

В `.env.local` можно включить `VITE_ENABLE_DEMO_TOOLS=true`.
Внизу появится ссылка на `/demo`. По умолчанию этот маршрут отключён.
Панель позволяет проверить все существующие операции Swagger:

- `GET /health` — состояние API и повторная проверка соединения;
- `POST /api/transactions` — зачисление, списание, возврат, внутренний перевод
  и кредитные средства с суммой, контрагентом и временем;
- `POST /api/events/account` — наложение и снятие ареста счёта;
- `POST /api/scenarios/{name}/run` — готовый профиль с историей;
- `POST /api/debug/advance-time` — сдвиг времени на заданное число часов.

Эти пять служебных операций дополняют десять операций обычного интерфейса:
анкета, PUT/PATCH правила, состояние копилки, снятие, история карты,
регулярные платежи и их исключение, решения и ответы.

Суммы в форме операций вводятся в рублях и отправляются в копейках.
Время вводится по Москве, в API уходит RFC 3339 UTC. После запуска сценария
или сдвига времени обе формы получают сценарную дату; при необходимости
её можно отредактировать. После успешного события счёта время следующего
увеличивается на секунду: бэкенд применяет только события новее предыдущего.
Статус ареста показывается из ответа сервера, даже если старое событие было
принято, но не изменило состояние счёта.

При потере ответа ID и полный запрос операции/события сохраняются для повтора
в текущей вкладке, включая перезагрузку. До подтверждения данные запроса
не редактируются, сценарный сброс и сдвиг времени заблокированы. Ответы 4xx
показываются рядом с формой и позволяют исправить запрос. POST-запросы
не повторяются автоматически. Балансы, операции и решения обновляются с API.

Запуск сценария требует отметить подтверждение сброса данных Ани;
сдвиг времени затрагивает весь сервер. Эти действия не запускаются автоматически.

## Проверки

```sh
npm test
npm run test:e2e
```

Браузерные проверки используют установленный Google Chrome (`channel: chrome`)
и отдельный Vite-сервер на порту 5174. Реальный бэкенд не нужен: API подменяется
ответами по Swagger, данные на сервере не меняются. Если Chrome не установлен,
его нужно установить либо настроить другой канал в `playwright.config.js`.

Проверяются денежные суммы, повтор снятия после потерянного ответа, правило,
пауза, ответы и очередь вопросов, конфликт 409, анкета и отказ, исключение
платежей, фильтры, ошибки сети и ширины 320/390/768 px.
Для панели дополнительно проверяются все пять типов операций, повтор после
потерянного ответа без второго зачисления, порядок событий ареста, восстановление
соединения с API и синхронизация времени форм со сценарием.
В `artifacts/` создаются снимки с тестовыми данными и сравнение геометрии
карточки с исходным HTML. Это проверка фронтенда с подменённым API;
полный прогон с работающей базой и бэкендом выполняется отдельно.

`node_modules/`, `.npm-cache/`, `dist/`, `test-results/` и `artifacts/` — локальные
зависимости и результаты запуска; исходники приложения от них не зависят.
