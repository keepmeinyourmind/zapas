# План реализации бэкенда «Запас» — спринт 1

Цель к 31 октября: `docker compose up` поднимает сервис, PostgreSQL и Swagger UI; пять демо-сценариев Ани работают через API и всегда дают одинаковый результат; по каждому решению видны действие, сумма и причина на русском; движок покрыт тестами.

Не делаем в спринте 1: Kafka, transactional outbox, Telegram-бот, счёт со сроком и штрафом (это новый банковский продукт — только на слайдах), ML.

---

## 1. Как работает продукт для клиента

1. Клиент подключает копилку: цель, сумма цели, срок (6/12/24 мес), процент от дохода (1–50%), порог поступления «не трогать поступления меньше N ₽». Новый клиент без истории дополнительно указывает примерный доход и тип дохода.
2. Приходит поступление на карту → классификатор решает, доход ли это.
3. Если доход — считаем безопасную сумму: деньги, которые останутся после обязательных платежей и повседневных трат до следующего дохода.
4. Движок решает: перевести автоматически, спросить клиента, пропустить или перевести и предложить поднять процент.
5. Если спросили, а клиент не ответил за 24 часа — срабатывает самый безопасный вариант (минимальная сумма или пропуск).

Порог для открытия счёта (минимальный первый взнос) **не вводим**: он отсекает студентов. Вместо этого — `MinIncome` (задаёт клиент) и `MinTransfer` (100 ₽).

---

## 2. Классификатор (`internal/classifier`)

Работает без истории, поэтому корректен и для нового клиента. Порядок проверок:

1. `TxKindInternal` (перевод из копилки или между своими счетами) → `IncomeNone`. **Первая проверка, защищает от цикла.**
2. `TxKindRefund`, `TxKindLoan`, `CounterpartySelf` → `IncomeNone`.
3. `CounterpartyLegal` с регулярностью около 15 или 30 дней → `salary` или `advance` (аванс меньше и раньше в месяце).
4. Известный отправитель-вуз или пометка «стипендия» → `scholarship`.
5. `CounterpartyLegal`, разово и больше медианы в 1,5 раза → `bonus`.
6. `CounterpartyPerson` → `freelance`, только если клиент раньше подтвердил этого отправителя; иначе `IncomeNone`.

ML не используем: нет данных для обучения, нужна объяснимость, ошибка дорогая. ML — после пилота, для серых зон.

## 3. Профиль дохода (`internal/profile`)

- Месячный доход = сумма доходов за календарный месяц; профиль = медиана за 3–6 месяцев. Аванс и зарплата складываются, поэтому аванс не выглядит как падение дохода.
- `Deviation` — отклонение дохода этого месяца от медианы в процентах (аванс сравниваем с авансами, зарплату с зарплатами).
- **Уровень доверия (холодный старт):**

| Уровень | Когда | Поведение движка |
|---|---|---|
| `TrustLevelLow` | меньше 2 месяцев истории | всегда спрашиваем, процент не выше заявленного; вместо медианы — `DeclaredIncome` из анкеты |
| `TrustLevelMid` | 2–3 месяца | автоперевод, если сумма близка к ожидаемой, иначе вопрос |
| `TrustLevelHigh` | больше 3 месяцев | полная логика |

Клиент, который давно в банке, но только подключил копилку, — не холодный старт: история уже есть.

**Регулярные платежи** (`profile/recurring.go`): группируем списания по получателю — не меньше 2 раз, сумма ±10%, интервал 25–35 дней. Платежи, которые клиент исключил вручную, пропускаем. `UpcomingUntil(date)` = обязательные платежи до следующего дохода + средние повседневные траты в день × дней до следующего дохода. Если не успеваем — обязательные платежи задаются прямо в сценарии.

## 4. Движок (`internal/engine`)

Чистая функция `Decide(in Input) domain.Decision`. Порядок проверок:

```go
// 1. Доход ли это и выше ли порога
if !in.Income.Kind.IsIncome() || in.Income.Amount < in.Rule.MinIncome → skip("не доход или ниже порога")
// 2. Пауза и цель
if in.Rule.Paused → skip("копилка на паузе")
if in.Savings >= in.Rule.GoalAmount → skip("цель достигнута")
// 3. Безопасная сумма — только собственные средства, без кредитного лимита
safe   := in.OwnBalance - in.Upcoming - in.Buffer
want   := in.Income.Amount.Share(in.Rule.SavePercent)
amount := min(want, max(safe, 0))
if amount < in.Rule.MinTransfer → ask/skip("впереди обязательные платежи")
// 4. Холодный старт
if in.Profile.Trust == TrustLevelLow → ask(amount, "мы ещё изучаем ваш доход")
// 5. Изменение дохода и разовые выплаты
switch {
case kind == bonus:          ask("пришла премия — отложить больше в этот раз?")
case deviation < -0.15:      ask(amount, "доход ниже обычного на N%")
case amount < want:          ask(amount, "через N дней платёж по ...")
case deviation > +0.15:      suggest_raise(amount, "доход вырос на N%")
}
return auto(amount, "доход в пределах обычного")
```

Варианты для `ask` (`Options`): рекомендуемая безопасная сумма, при возможности полный процент; «пропустить» есть всегда.

## 5. Сервис и переводы

**Оркестратор (`internal/service`)**, в одной транзакции БД:
1. Сохранить транзакцию; если ID уже есть — ничего не делать.
2. Классифицировать, загрузить профиль, правило, платежи, вызвать `Decide`.
3. Если у клиента уже висит вопрос (`pending`) — старый пометить `expired`, новый создать с объединённой суммой.
4. `auto` → сразу исполнитель; `ask` → `pending`, `expires_at = now + 24h`.

**Исполнитель переводов (`internal/transfer` или внутри service):**
- `SELECT ... FOR UPDATE` по клиенту, повторная проверка баланса (баланс мог измениться между решением и переводом).
- Если денег меньше — уменьшить сумму; если ниже `MinTransfer` — отменить.
- Вставка в `transfers` (уникальный `source_tx_id`) + обновление обоих балансов — одной транзакцией.

**Таймауты:** цикл раз в минуту: `pending` с истёкшим `expires_at` → безопасный вариант. Ответ после таймаута отклоняется с сообщением, что уже сделано. Для демо — `POST /api/debug/advance-time`.

## 6. Схема БД (`migrations/`)

| Таблица | Ключевые поля |
|---|---|
| `clients` | id, name, card_balance BIGINT, savings_balance BIGINT |
| `savings_rules` | все поля `domain.SavingsRule`, created_at |
| `transactions` | id PK, client_id, amount BIGINT, type, counterparty, counterparty_kind, occurred_at, income_kind, processed BOOL |
| `recurring_payments` | client_id, recipient, avg_amount, day_of_month, user_excluded |
| `decisions` | id, client_id, source_tx_id, action, amount, options JSONB, reason, status, created_at, expires_at NULL |
| `transfers` | id, decision_id, **source_tx_id UNIQUE**, client_id, amount, created_at |

Деньги — `BIGINT` (копейки), тот же диапазон, что `int64`.

## 8. Демо-сценарии (`internal/scenarios`)

Героиня — **Аня, 20 лет, студентка**: подработка 25 000 ₽ + стипендия 5 000 ₽ ≈ 30 000 ₽/мес; 25-го рассрочка за ноутбук 6 000 ₽; связь и подписки 1 000 ₽; цель «Подушка», 12 месяцев, 10%. Сценарий = история за 3–4 месяца + одно ключевое событие.

| Сценарий | Ключевое событие | Ожидаемое решение |
|---|---|---|
| `stable` | пришло 30 000 ₽ | `auto`, 3 000 ₽ |
| `income_drop` | пришло 24 000 ₽, через 5 дней рассрочка | `ask`, 1 000 ₽ или пропуск |
| `self_transfer` | 10 000 ₽ со своей карты другого банка | не доход, решения нет |
| `new_client` | первая зарплата без истории | `ask`, «мы ещё изучаем ваш доход» |
| `income_rise` | 36 000 ₽ третий месяц подряд | `auto` + предложение 12% (если успеваем) |

Повседневные траты и буфер в `income_drop` подогнать так, чтобы безопасная сумма вышла ровно 1 000 ₽ — так в раскадровке видео.

**Видео (2–3 мин):** слева экран телефона, справа история решений из API. Главная сцена — `income_drop`: обычная копилка молча списала 2 400 ₽ и на рассрочку не хватило 1 400 ₽, «Запас» спросил и предложил 1 000 ₽. Затем 5 секунд `self_transfer`, в конце `go test` зелёный.

## 9. Пограничные случаи

В код и тесты спринта 1:
1. Перевод из копилки обратно на карту — не доход.
2. Кредитные средства не участвуют в расчёте.
3. Минимальная сумма перевода.
4. Аванс не считается падением дохода.
5. Повторное событие транзакции — один перевод.
6. Новый доход, пока висит старый вопрос.
7. Цель достигнута.

Только на слайды / ответы экспертам: премии, фриланс от физлиц, сторно, отзыв согласия (152-ФЗ) → откат к простому режиму, арест счёта (115-ФЗ), несовершеннолетние (MVP только 18+), тихие часы для пушей, события не по порядку (сортировать по `occurred_at`).
