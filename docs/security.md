# Политика информационной безопасности и план защиты данных (Спринт 2)

Как специалист по информационной безопасности, я проанализировал архитектуру MVP и разработал план устранения уязвимостей для пилотного запуска в банке-партнёре (ВТБ).

## 1. Текущий статус MVP (осознанные ограничения)

В текущей демо-версии сознательно упрощены следующие механизмы для скорости разработки:
- Отсутствие аутентификации (клиент определяется по `id` в URL).
- Открытые отладочные эндпоинты (`/api/debug/*`, `/api/scenarios/*`).
- Эндпоинты приёма транзакций (`/api/transactions`) доступны без проверки источника.
- Отсутствует шифрование трафика (HTTPS) и соединения с БД (`sslmode=disable`).
- Данные анкеты хранятся в открытом виде.

## 2. План устранения уязвимостей для Пилота (Спринт 2)

### 2.1. Аутентификация и авторизация (AuthN / AuthZ)
- **Внешний контур**: Переход от передачи `client_id` в URL к валидации JWT-токена, выдаваемого банком (ВТБ Онлайн) через OAuth2 / OIDC.
- **Внутренний контур**: Эндпоинты `/api/transactions` и `/api/events/account` будут доступны **только** из внутренней сети банка. Реализация через mTLS (взаимная аутентификация по сертификатам) или строгий IP Whitelisting + API Key.

### 2.2. Защита периметра API
- **Удаление debug-эндпоинтов**: Полное отключение `/api/debug/*` и `/api/scenarios/*` в production-сборке через флаги компиляции или конфигурацию окружения.
- **Rate Limiting**: Внедрение ограничения частоты запросов (например, 100 req/min на IP) для предотвращения brute-force и DoS-атак.
- **Валидация входных данных**: Строгая проверка всех входящих JSON-полей на соответствие схемам OpenAPI (тип данных, длина, диапазоны).
- **Rate Limiting**: Реализовано в Спринте 1. Лимит 100 запросов в минуту на IP с использованием sliding window. При превышении возвращается `HTTP 429 Too Many Requests` с заголовком `Retry-After: 60`.

### 2.3. Защита данных (Data Protection)
- **Транспорт**: Принудительное использование HTTPS (TLS 1.3) для всех внешних запросов.
- **База данных**: Переключение PostgreSQL на `sslmode=require` или `verify-full` с валидацией сертификата сервера.
- **Данные анкеты**: Внедрение шифрования чувствительных полей (например, ФИО, телефон) на уровне приложения перед записью в БД (AES-256), ключи хранятся в KMS (Key Management Service) или переменных окружения, а не в коде.

## 3. Бизнес-логика и защита от фрода (моя реализация в MVP)

Уже на этапе MVP заложены критически важные механизмы безопасности:

### 3.1. Идемпотентность
Уникальный `source_tx_id` гарантирует, что повторная отправка одной и той же транзакции банком (например, из-за таймаута сети) не приведёт к двойному списанию средств (защита от Replay Attack).

### 3.2. Целостность финансовых расчётов
Все денежные суммы строго типизированы как `int64` (копейки). Использование `float` запрещено, что полностью исключает уязвимости округления (Salami Slicing attacks).

### 3.3. Детерминизм
Движок `Decide()` является чистой функцией, что позволяет легко покрывать его юнит-тестами и аудировать логику принятия решений без побочных эффектов.

## 4. Соответствие 152-ФЗ «О персональных данных»

Поскольку система анализирует финансовые паттерны, она обрабатывает ПДн. Для легитимной работы требуется:

### 4.1. Явное согласие
Добавление в UI банка чекбокса с текстом: *«Я даю согласие на анализ моих транзакций для расчёта безопасной суммы накоплений»*.

### 4.2. Право на забвение
Реализация эндпоинта `/api/clients/{id}/data-erasure` для полного анонимизированного удаления данных по запросу клиента.

### 4.3. Локализация
База данных и серверы размещаются исключительно на территории РФ.

## 5. Моделирование угроз (STRIDE) для ключевого сценария "Пополнение копилки"

| Угроза (STRIDE) | Описание атаки | Текущий статус (MVP) | Митигация в Спринте 2 |
| :--- | :--- | :--- | :--- |
| **Tampering** (Модификация) | Перехват запроса и изменение суммы списания. | Частично защищено: бэкенд валидирует схему запроса и использует `int64`. | Подпись запросов (HMAC) и строгая валидация на уровне API-шлюза банка. |
| **Information Disclosure** (Раскрытие) | IDOR-атака: подбор `client_id` в URL для просмотра чужих данных. | Уязвимо: нет аутентификации, `id` передается в пути. | Внедрение JWT-токенов. `client_id` будет извлекаться из claims токена, а не из URL. |
| **Repudiation** (Отказ от действий) | Пользователь заявляет: "Я не давал согласие на это списание". | Защищено: каждое решение логируется с уникальным `source_tx_id` и timestamp. | Добавление хэша цифрового согласия пользователя в транзакцию БД для аудита. |
| **Denial of Service** (DoS) | Flood-атака на API с целью перегрузки сервера. | Не защищено: нет rate limiting. | Внедрение middleware Rate Limiting (100 req/min на IP). |

## 6. Требования к безопасности клиентской части (Frontend)

- **CORS**: Строгие правила на бэкенде, разрешающие запросы только с доверенного домена фронтенда.
- **Валидация на клиенте**: Строгая проверка типов данных в формах перед отправкой для снижения нагрузки на бэкенд.
- **Управление секретами**: Токены и ключи API не хардкодятся в коде фронтенда, а передаются через переменные окружения (`.env`).
- **Защита от XSS**: Санитизация всех пользовательских данных перед отображением в UI.
